## Tradeoffs
- 2026-11-06T10:42:00Z — The `claim-sources` sensor rejects any claim block with no inline source tag, including short factual bullets such as a stakeholder's role. Rather than dropping those bullets or inventing a source, each one was tagged with the answer that actually grounds it, which forced the grounding check to be done by hand rather than left to the sensor.
- 2026-11-06T10:47:00Z — The approval-fingerprint and lifecycle tooling ships as a compiled binary, so a source patch to the sensor has no effect at runtime; the deliverables were shaped to satisfy the shipped sensor instead of the source.

- 2026-11-06T11:21:00Z — The reviewer binds its verdict to the artifact bytes captured at REVIEW_REQUESTED. Editing a deliverable after the reviewer returns makes `log review --verdict` refuse with "its output documents changed after review iteration 1 started", and `--retry-pending` cannot rebaseline the change either. The fixes therefore had to be applied before the review dispatch, not after it.
- 2026-11-06T11:59:00Z — The design-system scope could be closed either by enumerating all nine workbook section 11 token families in the bullet or by declaring the enumeration indicative and naming section 11 as authoritative. The second was chosen because the first would have copied a requirement list into a stage artifact that a later stage owns, and it would have frozen a partial token list into a scope claim. Naming the authoritative source keeps the requirement in one place and still leaves a builder able to find the complete list.
- 2026-11-06T12:14:00Z — A `[desc]` tag grounds the user's request, not derived decision-set detail. Three claims were tagged `[desc]` while asserting specifics the description string does not contain — the deferred-recovery wording, the pre-MVP metric qualifier, and the recovery-reason / distinct-audit-action rule. The content was correct against upstream in all three cases; only the citation was wrong. The fix was to extend the workbook-enumeration rule with the §4.1 recovery detail it now has to carry, rather than to tag the claims with a rule that does not mention them.
- 2026-11-06T12:16:00Z — The reviewer binds its verdict to the artifact bytes captured at REVIEW_REQUESTED, and the same binding applies to the review file itself: the appendix must BEGIN with the `## Review` heading, with the `**Reviewer:**` / `**Verdict:**` / `**Iteration:**` authority lines inside it. A review that opens with the authority lines above the heading is rejected as "must be terminal and contain no later rendered H1 or H2 heading" even when it has only one heading and no later H1/H2 at all.
- 2026-11-06T12:35:00Z — A `[memory:M<n>]` rule must carry the words of the claim it grounds, not merely point at where the claim lives. Pointing at a section is not carrying it: a rule that names "the metric qualifiers the population relies on" grounds nothing about pre-MVP backfill, and a reader following the tag still does not land on the asserted content. Each rule that a deliverable cites has to restate the requirement in the terms the deliverable uses.
- 2026-11-06T12:36:00Z — Extending a rule to carry a claim changes the rule's bytes, and every `[memory:M<n>]` register line across every file that cites it is a byte-for-byte copy of that rule. The register lines are therefore regenerated programmatically after every rule edit rather than hand-edited, and verified against the `## Decided` entries before the sensors run.
- 2026-11-06T12:55:00Z — The `required-sections` and `upstream-coverage` sensors read the file passed as `--output-path`; pointing them at a freshly created empty scratch file measures that empty file, not the deliverable. They must be fired against the deliverable path itself, and the sensor's finding lands in the engine's own `.aidlc-engine/sensors/` file rather than in the deliverable.
- 2026-11-06T12:57:00Z — A rejection needs a HUMAN_TURN recorded after the last gate-resolution event, and the redo jump resets the stage to `in-progress`, so the sequence for a revision round is: jump → re-run the stage's summary confirmation → re-review → present the gate → wait for the human's reply → `report --result rejected` → `report --result revised` → jump. Reporting the rejection before the human replies at the re-presented gate is refused, because the summary-confirmation receipt is itself a gate resolution and consumes the human turn that preceded it.
