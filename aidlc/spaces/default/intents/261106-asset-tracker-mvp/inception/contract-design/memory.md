2026-11-10T12:05:00Z — read the stage's contract-mechanism choice as a question about what crosses each boundary rather than as a single mechanism for all boundaries: shared schema where a database or shared model is the agreement, in-process interface for a direct call, and an HTTP API only where the consumer is outside the process. On a single-process release this yields no service boundaries, and every contract still gets a named payload, an owner, and an explicit failure behaviour — an internal call is a contract too, and "internal" is not a reason to leave it unspecified. The shared vocabulary stays centrally owned by the unit that provides it, versioning is deliberately not introduced, and one failure policy per boundary kind replaces a policy restated on every edge. Domain error semantics and HTTP status translation are split: the domain vocabulary owns the error codes, and the presentation/API boundary owns their HTTP exposure.
